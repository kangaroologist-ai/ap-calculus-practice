# Reviewer B · Motion and feel (Sonnet, emil-design-eng + apple-design), 2026-09-27

Verbatim report returned by the read-only reviewer for T1b.

**Summary:** The long-press bubble and the dimming/shift mechanics are largely unspecified for motion, and the one real visual bug I can confirm from the screenshots is that ⇧ one-shot and ⇧ locked are not reliably distinguishable — the rest are unspecified feel/timing gaps that will bite fast typists if left to an implementer's defaults.

Sources: `proto2-normal-light.png`, `proto2-shift-light.png`, `proto2-lock-dark.png`, `proto2-incorrect-light.png`, `proto2-stale-light.png`, `proto2-correct-dark.png` (screenshots); `docs/design/DESIGN.md` §6.3 (key press = background swap only, no transition, flagged P2), §7 (motion frequency table, reduced-motion rule); `plan.md` S2/S6 (reasoning from the written spec, bubble itself "not mocked yet").

| # | Before (proposal as described/shown) | After (recommendation) | Why | Grade |
|---|---|---|---|---|
| 1 | 300 ms long-press threshold to arm the alt bubble (plan S2), no minimum finger-stillness requirement | Raise arm delay to ~450 ms and require the touch point stay within ~6 px before the timer starts counting (else treat as a drag, not a hold) | A student pausing mid-keystroke to think (very common on `sin`/`cos`/`e^` keys, used in ~23%/23%/17% of answers per the plan's data) will hit 300 ms by accident; iOS's own press-and-hold affordances sit closer to 450–650 ms, so this also avoids racing the OS gesture in row 2 | P1 |
| 2 | Bubble is a custom hold gesture on keycaps; no mention of suppressing iOS Safari's native touch-and-hold (callout menu / text selection / haptic click) | Add `touch-action: manipulation; -webkit-touch-callout: none; -webkit-user-select: none;` to every keycap and swallow `contextmenu`/`touchstart` default on the keyboard container; verify on a real iPhone, not just WebKit emulation (DESIGN.md §6.5 already notes emulation can't reproduce iOS press behavior) | Without this, a 300–450 ms hold on iOS Safari can pop the system Select/Copy/Look Up menu at the same time as the custom bubble, visually colliding with or silently cancelling it | P1 |
| 3 | `proto2-shift-light.png` (one-shot) and `proto2-lock-dark.png` (locked) both show the same solid up-arrow glyph; the only difference across the two screenshots is theme (light vs dark) and a slightly deeper blue fill | Give the three states three distinct icon shapes, not fill-depth: outline arrow = off, filled arrow = one-shot, arrow-with-underline (or filled arrow in a filled square, mirroring iOS's own shift/caps-lock glyphs) = locked | A fill-depth-only distinction fails "not color/shade alone" and is genuinely hard to read at a glance mid-typing; borrowing the iOS shift/caps-lock shape distinction reuses a pattern students already know (familiarity principle) instead of inventing a new one | P1 |
| 4 | Bubble appear/disappear motion is unspecified ("not mocked yet, judge from the description") | Enter: opacity 0→1 + scale 0.95→1 over 120 ms `cubic-bezier(0.23,1,0.32,1)`, `transform-origin: bottom center` over the key. Release-to-insert: no animation, bubble vanishes the same frame the glyph commits. Slide-off-to-cancel: 80 ms opacity-only fade, no scale | Matches "feedback on press, continuous during interaction" and Emil's tooltip guidance (125–200 ms, ease-out, origin-aware); keeping insertion animation-free preserves the "typing must never animate" rule, while a quick plain fade on cancel reads as "nothing happened," not "something launched and came back" | P2 |
| 5 | Long-press behavior on a key with no alt (e.g. `(`, a bare variable key) is unspecified — implicitly the same 300 ms timer runs and simply produces no bubble | Don't arm the timer at all on `pointerdown` for a no-alt key; it must behave exactly like an ordinary tap with zero added latency on release | If the no-alt path shares the same timer/dispatch logic as alt keys, a slightly-held tap on a common key risks a perceptible delay before the character commits — unacceptable on a keyboard used hundreds of times per session | P2 |
| 6 | Non-alt keys dim while ⇧ is active (seen in `proto2-shift-light.png`: `÷`, `x`, `.` are visibly greyed); transition speed/property not specified | Opacity 1 → ~0.35 over 120 ms, opacity-only (no `transition: all`), consistent with DESIGN.md §7's `--dur-fast` color/opacity-only rule for state changes; the key must remain immediately tappable during its own fade | Keeps the dim consistent with the project's existing motion contract and reduced-motion rule; a key that "looks disabled" while fading must not actually lag input, or it will feel broken the first time a student taps mid-fade | P2 |
| 7 | After editing a wrong answer (`proto2-stale-light.png`), the border reverts to normal blue and the strip greys out — two visual changes, timing/sync unspecified | Drive the border-color revert and the strip's opacity/color fade off the same input event with the same duration (~150 ms ease, color/opacity only) | Apple's harmony principle: simultaneous cues that change on different timers read as glitchy; this also reuses DESIGN.md §7's existing pattern for feedback-box color transitions rather than inventing a new one | P2 |
| 8 | Reduced-motion handling for the *new* elements (bubble, dim/undim, strip cross-fade) isn't called out — DESIGN.md §7's reduced-motion rule only documents existing components | Explicitly extend the reduced-motion contract: bubble drops its scale (0.95→1) and keeps only the opacity fade; dim/undim and strip fades are already opacity/color-only so no change is needed — just state this in the spec so it isn't missed in implementation | DESIGN.md already promises project-wide "no displacement/scale under reduced motion, keep color/opacity," but that promise lives in one CSS rule (`style.css:1373`) scoped to today's components; new code paths need to be added to it explicitly or they'll ship un-covered | P3 |
| 9 | The 3 s correct-state countdown line (`proto2-correct-dark.png`) has no stated implementation approach | Reuse the existing 50 ms-linear-tick direct-width-update pattern already used for the auto-advance bar (DESIGN.md §7) rather than a CSS `transition: width 3s linear`; editing the field or pressing Next mid-countdown must cancel/hide it with no exit animation | A CSS-transition-driven countdown can't be cleanly interrupted (Apple's interruptibility principle) if the student edits or advances early; the project's own per-tick pattern already handles this correctly elsewhere | P3 |

One thing to flag back to the owner rather than treat as a finding: DESIGN.md §6.3 already documents that base key presses get *no* animation (background swap only, marked P2 as an accepted trade-off) — that's correct per the "100+ times/day → no animation" rule and should stay as-is; it's the *new* long-press/shift/strip elements above that lack a motion spec.
