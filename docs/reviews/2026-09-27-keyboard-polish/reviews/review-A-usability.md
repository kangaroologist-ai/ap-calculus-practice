## Reviewer A (usability & standards) — keyboard-polish prototype-2

Overall: the single-page + ⇧/long-press alt system is a real improvement over the two-page layout, and the in-box status strip is consistent with the existing correct/incorrect/inconclusive pattern. The two biggest problems are (1) alts have **zero discoverability affordance** in the resting state, and (2) the "no-alt, dimmed" keycaps in ⇧ mode measure well under WCAG AA text contrast while remaining fully live buttons.

| # | Finding | Evidence | Grade | Recommendation |
|---|---|---|---|---|
| 1 | Fact. In the resting keyboard, keys with an alt look pixel-identical to keys without one — no dot, tick, or texture marks them. A student has no way to learn that 7→x, 8→y, the fraction key→÷, or ▫^▫→[v]^▫ exist, short of accidentally double-tapping ⇧ or holding a key for 300 ms. | `proto2-normal-light.png`: all 1st-row keys (sin, cos, tan, 7, 8, 9, fraction, x, ⇧) render with identical weight/style. | P1 | Since the owner already rejected printed corner labels (`proto-alt11-light.png`), add a much lighter always-on cue that isn't a full label: e.g. a 2–3 px tint dot in one corner, or a subtly different keycap background for "has alt" keys. Pair it with one line in `help.html`/onboarding ("Hold a key, or tap ⇧, to see more symbols") — right now neither the UI nor (per DESIGN.md diff) the docs teach this gesture at all. |
| 2 | Fact (measured). Keys with no alt are shown dimmed while ⇧ is active — including operators students still need mid-entry (`+`, `−`, `.`, `)`, the plain variable key). Sampling `proto2-shift-light.png`, the dimmed glyph pixel is `rgb(156,156,158)` on a `rgb(246,246,248)` keycap → **contrast ≈ 2.5:1** (edge pixel; even a darker stroke-center estimate of `rgb(120,120,122)` only reaches **≈4.1:1**). WCAG 1.4.3 requires 4.5:1 for normal text, and these are not disabled controls (they're one tap away from full function). | Screenshot `proto2-shift-light.png`, pixel sample at (972,963) vs (1000,930); computed via standard relative-luminance formula. | P1 | Don't dim by lightening the glyph — dim by desaturating/graying the *background* instead, or keep the glyph at full `--label` contrast and use a lighter secondary cue (e.g. slightly reduced icon weight) so every visible operator clears 4.5:1 even mid-⇧. Add this state to `tests/contrast.test.ts` per DESIGN.md §3.1's own rule that new color/opacity states must be tested. |
| 3 | Fact. In `proto2-lock-dark.png`, the ⇧ key's "locked" state is shown only by a thin ~2×10 px underline beneath the arrow glyph, and the locked key's background (`rgb(30,48,66)`) is a hue-only shift from the neighboring unpressed key (`rgb(28,28,30)`) — contrast ratio between them is ≈1.1:1 (measured). Compare `proto2-shift-light.png`'s one-shot state, which gets a clearly lighter blue background wash. | Pixel samples: shift key bg (30,48,66) vs sibling key bg (28,28,30) in `proto2-lock-dark.png`; visual comparison of underline size across `proto2-shift-light.png` vs `proto2-lock-dark.png`. | P2 | Locked vs one-shot is the state a student is most likely to get stuck in (they forget they're still in ⇧ and every tap inserts the wrong glyph). Give locked mode a background wash with the same luminance delta the light theme gets, not just a small underline — WCAG 1.4.11 (non-text contrast) wants ≥3:1 for the UI-state indicator itself. |
| 4 | Fact. `proto2-correct-dark.png` shows the on-keyboard confirm key still reading "Check" (blue) at the same moment the in-box strip already reads "✓ Correct" with the countdown bar filling. The desktop equivalent (`proto2-desktop-correct-light.png`) *does* relabel its button to "Next question →" at that point. DESIGN.md §6.1 rule 7 says the confirm key must equal Next once correct. | Compare `proto2-correct-dark.png` (mobile keyboard key = "Check") against `proto2-desktop-correct-light.png` (button = "Next question →") for the same verdict state. | P1 (pending confirmation it's not just a stale mock) | Verify with the implementer whether this is mock lag or a real gap; if real, the keyboard confirm key's Check→Next relabel must fire in the same paint as the strip, or a student will tap "Check" again expecting to submit and get an unexpected "next question" jump. |
| 5 | Opinion, grounded in spec text. Per plan.md S6/G11, a long wrong answer's status text "fades at the end but stays visible" and the answer itself sits directly above the strip with only a thin rule between them (`proto2-incorrect-light.png`). For a long incorrect expression, the fade-out is exactly where a subtle error (e.g. a missing negative, a mismatched inner-derivative factor) is most likely to be — the visual technique that keeps the box compact risks hiding the very content the student needs to re-read. | `proto2-incorrect-light.png` (short example: `3x²·sin(x³)`); spec text in `plan.md` line 188 ("长答案的末尾淡出但仍可见"). | P2 | Confirm the fade only clips visually-overflowing characters and that horizontal scroll-to-caret still lets the student scrub through the full expression; don't rely on "still in the DOM" as sufficient when the visible/legible portion is what matters for review. |
| 6 | Fact. Reaching an alt requires either a tap-hold gesture (300 ms) or the ⇧ toggle — both are pointer/touch-only interactions. DESIGN.md §6.5 already documents that MathLive's virtual keyboard has no `role="tab"`/keyboard navigation, so this was already a known gap; the new alt system adds functions (arcsin, sec², [v]^▫, √[v], ÷, etc.) that are unreachable by a keyboard-only or switch-access user driving the *virtual* keyboard, where before they were reachable by a plain tap on the More page. | Spec `plan.md` S3 (⇧ tap/hold only); DESIGN.md §6.5 known-limitations list (no update proposed for this change per plan's To Do P3). | P2 | Add a line to DESIGN.md §6.5 noting that alt functions are touch/mouse-hold only and are unreachable via the virtual keyboard's own focus order; confirm (as the plan's other reviewers should too) that a student who genuinely cannot use touch/hold gestures still has a path — typing directly into the math-field with a physical keyboard bypasses this entirely, which is probably the intended fallback, but it isn't stated anywhere. |
| 7 | Fact/opinion. The status-strip copy set is "✓ Correct" / "! Not quite." / "i Couldn't check." — terse and consistent with existing copy voice (DESIGN.md §9: no periods on buttons, plain declarative sentences elsewhere). Good. One nit: "! Not quite." uses a period after a 2-word fragment while the desktop feedback panel historically read "Not quite." only (no leading "!") — the "!" plus period reads slightly redundant as a double stop/emphasis mark stacked with a full stop right after. | `proto2-incorrect-light.png`, `proto2-desktop-incorrect-light.png`. | P3 | Minor; consider "Not quite." without the leading "!" glyph if the icon-before-text pattern (established elsewhere as ✓/!/i, DESIGN.md §5.3) already carries the "wrong answer" signal — having both the "!" icon-letter and inline "!" reads slightly duplicated. Not a blocker. |

### What DESIGN.md should change
- §6.1 rule 4 ("除...外任何命令不在两页同时出现") is already flagged in plan.md D8 as needing a rewrite to "每个功能只出现一次：主字或 alt" — confirm that rewrite also states the new no-affordance-for-alts fact explicitly, since it's a discoverability regression relative to the two-page design (previously all functions were visible on some page).
- §6.4 (screen-reader names) needs entries for the ⇧ key itself (recommend "Shift", with state conveyed via `aria-pressed`) and for how alt-mode tooltip names change (e.g. does `tan` become "inverse tangent" when ⇧ is active, and is that update announced?) — not shown in any screenshot, worth adding to the S3 acceptance checklist.
- §6.5 known-limitations should gain the touch/hold-only alt-access note from finding 6.
- §3.1 contrast table/`tests/contrast.test.ts` should gain whatever token is used for "no-alt, dimmed" keycaps once finding 2 is fixed, so a regression can't reintroduce sub-4.5:1 text.
