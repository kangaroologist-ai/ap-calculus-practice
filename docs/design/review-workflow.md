# 发布前设计审核流程

目的：在用户看到之前，发现“测试全过、但用起来不对”的问题。v1.1.1 的键盘遮挡回归和 v1.2.0 之前的键盘排列问题，都属于几何断言通过、却没人从使用者角度看过的情况。本流程与 [`DESIGN.md`](DESIGN.md) 配套：DESIGN.md 规定“应该是什么样”，本流程规定“发布前怎么确认”。

## 1. 两级审核

| | 常规审核 | 完整审核 |
|---|---|---|
| 何时做 | 每次要提升 `package.json` 版本号（`AGENTS.md` 定义的用户可见改动） | 只在以下情况：新增界面或组件；修改 DESIGN.md 的原则或令牌；较大改版；用户要求 |
| 范围 | 只看本次与设计相关的改动（第 2 节确定范围） | 本次改动影响的界面状态及其相邻状态；修改 DESIGN.md 的原则或令牌时为整个网站 |
| 谁做 | Claude；改动范围大、需要看的状态多时，可以另派一个 Sonnet 只读评审者做前后截图对比 | 一个 Sonnet 只读评审者，使用合并式评审技能 `design-review`（第 4 节），一次完成三个视角；Claude 核实与定级 |
| 是否调用评审技能 | 不调用 | 调用 |
| 产出 | 任务文档里的一节“发布前审核”，或同目录的 `release-review.md` | `release-review.md` 加评审原文 |

纯重构、只改测试、只改内部文档不需要审核，在任务文档里写明“无需设计审核”及原因。

## 2. 常规审核的步骤

1. **确定范围**：用 `git diff <上一个发布提交>..HEAD --stat` 列出改动的文件，按下表找到受影响的界面状态；再加上 What's new 窗口（每次发布都会变）。

   | 改动的文件或部分 | 要看的状态（截图编号） |
   |---|---|
   | `src/math-keyboard.ts`、样式表的键盘一节 | 03 键盘打开、04 点按后、05 ⇧ 与长按（一次性、锁定、气泡），390 px 浅色 / 深色，1280 px |
   | `src/main.ts` 中的判分、按钮、焦点逻辑 | 06 答对、07 答错、08 无效、09 提示、10 完整解析 |
   | 对话框相关代码或样式 | 12 Move progress、13 What's new |
   | 令牌、全局样式、`src/style.css` 的基础部分 | 全部状态（相当于全量前后对比） |
   | `help.html` | 14 帮助页 |
   | 学习路径相关 | 11 学习路径 |

2. **截图**：启动开发服务器，运行 `npm run design:capture`；上一版本的截图在 `artifacts/design/<上一版本>/`，没有就检出上一个发布提交再生成一次。
3. **比对**：只打开范围内的状态，和上一版本对比；逐条对照 DESIGN.md 中与这些状态相关的规则和第 6 节清单里的相关项。自动测试已经断言的项（例如键盘几何、按压和减少动态）看测试结果即可，不必重复测量。
4. **定级与处理**：按下方标准定级。P0 / P1 修复后重做受影响状态的比对；P2 / P3 写进下一份任务文档，或写明接受的理由。
5. **真机确认**：涉及键盘、触控或安全区的改动，请用户在 iPhone 上确认一次。
6. **记录**：结论写进任务文档（第 7 节的格式），随发布提交。

## 3. 完整审核的步骤

| 步骤 | 负责人 | 内容 | 产出 |
|---|---|---|---|
| ① 截图 | Claude | 同常规审核第 2 步 | `artifacts/design/<版本>/` |
| ② 评审 | Sonnet × 1，只读 | 使用 `design-review` 技能，一次完成三个视角（见第 4 节） | 一份文字报告 |
| ③ 核实定级 | Claude | 逐条核实（能测量的自己测），按 P0–P3 定级，判断是否与 DESIGN.md 冲突；**与任务 Spec 冲突的结论不直接修改，先回到任务文档的 Grill 问负责人** | `release-review.md` |
| ④ 处理 | Claude（必要时委派代码修改） | 同常规审核第 4 步 | 修复提交 |
| ⑤ 真机确认 | 用户 | 同常规审核第 5 步 | 用户确认记录 |
| ⑥ 存档 | Claude | 报告原文、核实结论、关键截图存入 `docs/reviews/<日期>-<主题>/` | 提交 |

**定级标准**

| 级别 | 含义 | 是否阻塞发布 |
|---|---|---|
| P0 | 无法完成任务、数据丢失、内容被遮挡、无法访问 | 阻塞 |
| P1 | 明显违反 DESIGN.md 的原则或键盘规则、严重误导、无障碍 AA 不达标 | 阻塞 |
| P2 | 影响体验但有替代路径；局部不一致 | 不阻塞，进下一轮计划 |
| P3 | 打磨项 | 不阻塞 |

## 4. 合并式评审技能（仅完整审核）

技能文件：[`.claude/skills/design-review/SKILL.md`](../../.claude/skills/design-review/SKILL.md)（随仓库提交）。它不复制评审技能的内容，而是让评审者在一次评审中依次调用三套已安装的技能（`~/.claude/skills/` 与 Anthropic 的 design 插件），合并重复项，并逐条标注是否与任务 Spec 冲突：

| 视角 | 技能 | 重点 |
|---|---|---|
| A · 可用性与规范 | `design:design-critique`、`design:accessibility-review`、`design:ux-copy`（改了令牌或组件时加 `design:design-system`） | 层级、一致性、WCAG AA、令牌使用、文案 |
| B · 动效与手感 | `emil-design-eng`、`apple-design` | 按压反馈、动画频率、时长缓动、减少动态、触屏行为 |
| C · 整体评审与打磨 | `impeccable` 的 `critique`、`polish` | 启发式评估、认知负荷、打磨清单 |

报告格式由技能规定：一张按 P0–P3 排序的问题表（视角、事实或观点、证据、具体改法、机械修改或需要设计判断、是否与 Spec 冲突），加上 “已看过且没有问题的状态”、DESIGN.md 需要改的地方和未能验证的项。

impeccable 的检测器是它首次运行时下载的可执行文件。除非用户对该次发布明确同意，否则不运行；不运行时，报告开头必须带 impeccable 规定的降级标记。

**可选：三人独立评审。** 负责人要求多个互不影响的意见时（例如实现前对样机的评审），改派三个 Sonnet 只读评审者，各用上表一个视角，并行进行、互相看不到结果，Claude 综合。2026-09-27 键盘改版实现前的样机评审就是这样做的（`docs/reviews/2026-09-27-keyboard-polish/reviews/`）。

## 5. 评审背景（仅完整审核）

派评审者时，先写一份共同背景（放在任务目录的 `reviews/context.md`），再让评审者按 `design-review` 技能执行（可选的三人评审时，再给每人一段视角说明）。共同背景至少包括：

1. 仓库路径、产品简介（手机优先、离线、无账号、英文界面）、主要文件（`src/main.ts`、`src/style.css`、`src/math-keyboard.ts`、`help.html`）。
2. 本次改动的范围（要看哪些界面状态）和对应的 Spec 编号；任务文档 `plan.md` 的路径；上一版本与候选版本截图目录的路径；开发服务器地址。
3. DESIGN.md 的路径，并要求评审“以 DESIGN.md 为基准，指出违反之处，也指出 DESIGN.md 本身不合理的地方”。
4. 规则：
   - **只读**：不改仓库里的任何文件。
   - **报告用文字返回**：子代理无法写报告文件，最终回复就是报告。
   - **不用共享浏览器窗格**：需要补截图时，在自己的 scratchpad 里写 Playwright 脚本，用 `node --import tsx` 运行。
   - **不安装、不运行第三方可执行文件**。
   - **区分事实和观点**：写明元素、`文件:行号` 或选择器、测量值；注明结果来自 Playwright 仿真还是真机。
   - 报告控制在约 1,800 字以内，结尾按 P0–P3 排序，并标明每项是机械修改还是需要设计判断。

## 6. 审核清单

常规审核只核对与改动范围相关的项；完整审核逐项核对与改动范围相关的项（修改了原则或令牌时全部核对）。结果写进任务文档或 `release-review.md`。

**原则**（DESIGN.md 第 2 节）
- [ ] 每个界面状态最多一个主按钮；禁用的控件没有主按钮样式。
- [ ] 触屏上没有依赖悬停的信息，没有残留的悬停高亮或气泡。

**令牌与组件**（第 3、5 节）
- [ ] 新增或修改的样式只用令牌，没有新的原始颜色、间距、圆角、阴影、时长。
- [ ] 按钮的默认、悬停、按下、焦点、禁用状态齐全。
- [ ] 四种判定结果在颜色以外都有区分（✓ / ! 符号，或 “Check your input” 加框下原因的文字）。

**数学键盘**（第 6 节；前四项同时由 `tests/math-keyboard-layout.test.ts` 与 `tests/visual-tokens.spec.ts` 检查）
- [ ] 每行 9 个单位；数字块在第 4–6 列；每个功能只出现一次（主功能或 alt）；← → ⌫ 与确认键的 alt 与自身相同。
- [ ] 390 px 下左右留白 ≤ 6 px；功能键图标偏移 ≤ 1 px；⇧ 关 / 一次性 / 锁定三态可区分；⇧ 打开时有 alt 的键为 `--tint`、没有 alt 的键不变淡。
- [ ] 点按后 1.5 秒没有悬停气泡；长按有 alt 的键 450 ms 出现 alt 气泡，松手输入、移出取消；没有编辑工具栏。
- [ ] 所有设备：答对、答错、无效的结果显示在答题框里，无效时框下有原因小字；手机键盘打开时这些不被键盘遮挡；点提示后提示面板至少露出开头；确认键在判分前后分别显示 Check / Next；顶栏左侧 Hint?、Skip，右侧收起。
- [ ] 题库答案用到的运算都能从键盘取得（主功能或 alt）。

**动效**（第 7 节）
- [ ] 高频操作没有动画；其余动画只用动效令牌，进入用 ease-out。
- [ ] 减少动态模式下没有位移、缩放、彩纸，颜色和透明度过渡仍在。

**无障碍**（第 8 节）
- [ ] `tests/contrast.test.ts` 与 `tests/visual-tokens.spec.ts` 通过。
- [ ] 触控目标 ≥ 44 px（键盘键宽例外）；每页一个 `h1`；键盘每个键有读音名称。

**截图**
- [ ] 390 / 1280 × 浅色 / 深色的截图矩阵都看过，并与上一版本对比。
- [ ] 截图一律是视口截图（整页截图会把固定定位的键盘画到页面中间）。

**文档**
- [ ] README、`help.html`、What's new 与改动一致（`AGENTS.md` 的文档同步规则）。
- [ ] DESIGN.md 已更新，或在任务文档中写明不需要更新的理由。

## 7. 记录

记录至少包括：审核级别（常规或完整）及理由、候选提交哈希、改动范围与对应的截图状态、截图目录、问题表（来源、是否核实、级别、处理方式）、相关清单项的结果、真机确认结果、最终结论（可以发布或阻塞）。完整审核还要写明评审原文的位置，以及哪些结论与 Spec 冲突、已回到 Grill。
