# 发布前设计审核流程

目的：在用户看到之前，发现“测试全过、但用起来不对”的问题。v1.1.1 的键盘遮挡回归和 v1.2.0 之前的键盘排列问题，都属于几何断言通过、却没人从使用者角度看过的情况。本流程与 [`DESIGN.md`](DESIGN.md) 配套：DESIGN.md 规定“应该是什么样”，本流程规定“发布前怎么确认”。

## 1. 什么时候做

- **必须做**：任何要提升 `package.json` 版本号的改动，即 `AGENTS.md` 定义的用户可见改动（行为、流程、按钮文字、提示信息、课程或进度规则）。
- **不用做**：纯重构、只改测试、只改内部文档。任务文档里写明“无需设计审核”及原因。
- **可以缩小范围**：只改了一个界面时，截图矩阵照常全量生成，但评审重点放在改动的界面，其余界面只做前后对比。

## 2. 步骤与负责人

| 步骤 | 负责人 | 内容 | 产出 |
|---|---|---|---|
| ① 截图 | Claude | 启动开发服务器，运行 `npm run design:capture`，生成候选版本的截图矩阵；同时准备上一版本的截图（`artifacts/design/<上一版本>/`，没有就检出上一个发布提交再生成一次） | `artifacts/design/<版本>/` |
| ② 独立评审 | Sonnet × 3，并行、只读 | 每人一个固定视角（见第 3 节），互相看不到对方结果 | 三份文字报告 |
| ③ 综合定级 | Claude | 逐条核实（能测量的自己测），合并重复项，按 P0–P3 定级，并判断是否与 DESIGN.md 冲突 | 任务目录下的 `release-review.md` |
| ④ 处理 | Claude（必要时委派） | P0 / P1 修复后重新走 ①–③；P2 / P3 写进下一份任务文档，或在 `release-review.md` 里写明接受的理由 | 修复提交 |
| ⑤ 真机确认 | 用户 | 涉及键盘、触控或安全区的改动，在 iPhone 上确认一次 | 用户确认记录 |
| ⑥ 存档 | Claude | 报告原文、综合结论、关键截图存入 `docs/reviews/<日期>-<主题>/` | 提交 |

**定级标准**

| 级别 | 含义 | 是否阻塞发布 |
|---|---|---|
| P0 | 无法完成任务、数据丢失、内容被遮挡、无法访问 | 阻塞 |
| P1 | 明显违反 DESIGN.md 的原则或键盘规则、严重误导、无障碍 AA 不达标 | 阻塞 |
| P2 | 影响体验但有替代路径；局部不一致 | 不阻塞，进下一轮计划 |
| P3 | 打磨项 | 不阻塞 |

## 3. 三套评审视角

三个视角各自独立，避免互相影响判断。技能已经安装在 `~/.claude/skills/`，Anthropic 的 design 技能以插件形式提供。评审者通过 Skill 工具调用这些技能。

| 视角 | 技能 | 重点 | 报告格式 |
|---|---|---|---|
| A · 可用性与规范 | `design:design-critique`、`design:accessibility-review`、`design:design-system`、`design:ux-copy` | 层级、一致性、WCAG AA、令牌使用、文案 | 问题表 + P0–P3 |
| B · 动效与手感 | `emil-design-eng`、`apple-design` | 按压反馈、动画频率、时长缓动、减少动态、触屏悬停 | Before / After / Why 表 + P0–P3 |
| C · 整体评审与打磨 | `impeccable` 的 `critique`、`polish` | Nielsen 十项评分、认知负荷、用户画像、打磨清单 | impeccable 报告格式 + P0–P3 |

impeccable 的检测器是它首次运行时下载的可执行文件。除非用户对该次发布明确同意，否则不运行；不运行时，报告开头必须带 impeccable 规定的降级标记。

## 4. 评审提示词模板

派评审者时，先写一份共同背景（放在任务目录的 `reviews/context.md`），再给每人一段视角说明。共同背景至少包括：

1. 仓库路径、产品简介（手机优先、离线、无账号、英文界面）、主要文件（`src/main.ts`、`src/style.css`、`src/math-keyboard.ts`、`help.html`）。
2. 本次改动的范围和对应的 Spec 编号；上一版本与候选版本截图目录的路径。
3. DESIGN.md 的路径，并要求评审“以 DESIGN.md 为基准，指出违反之处，也指出 DESIGN.md 本身不合理的地方”。
4. 规则：
   - **只读**：不改仓库里的任何文件。
   - **报告用文字返回**：子代理无法写报告文件，最终回复就是报告。
   - **不用共享浏览器窗格**（三人并行）：需要补截图时，在自己的 scratchpad 里写 Playwright 脚本，用 `node --import tsx` 运行。
   - **不安装、不运行第三方可执行文件**。
   - **区分事实和观点**：写明元素、`文件:行号` 或选择器、测量值；注明结果来自 Playwright 仿真还是真机。
   - 报告控制在约 1,800 字以内，结尾按 P0–P3 排序，并标明每项是机械修改还是需要设计判断。

## 5. 审核清单

Claude 在综合阶段逐项确认，结果写进 `release-review.md`。

**原则**（DESIGN.md 第 2 节）
- [ ] 每个界面状态最多一个主按钮；禁用的控件没有主按钮样式。
- [ ] 触屏上没有依赖悬停的信息，没有残留的悬停高亮或气泡。

**令牌与组件**（第 3、5 节）
- [ ] 新增或修改的样式只用令牌，没有新的原始颜色、间距、圆角、阴影、时长。
- [ ] 按钮的默认、悬停、按下、焦点、禁用状态齐全。
- [ ] 反馈框四种判定都有颜色以外的图标。

**数学键盘**（第 6 节；前四项同时由 `tests/math-keyboard-layout.test.ts` 与 `tests/visual-tokens.spec.ts` 检查）
- [ ] 每行 9 个单位；数字块在第 4–6 列；导航键两页同位；函数和结构键不跨页重复。
- [ ] 390 px 下左右留白 ≤ 6 px；功能键图标偏移 ≤ 1 px；两页等高。
- [ ] 点按后 1.5 秒没有气泡；没有编辑工具栏。
- [ ] 题库答案用到的运算都在 Main 页。

**动效**（第 7 节）
- [ ] 高频操作没有动画；其余动画只用动效令牌，进入用 ease-out。
- [ ] 减少动态模式下没有位移、缩放、彩纸，颜色和透明度过渡仍在。

**无障碍**（第 8 节）
- [ ] `tests/contrast.test.ts` 与 `tests/visual-tokens.spec.ts` 通过。
- [ ] 触控目标 ≥ 44 px（键盘键宽例外）；每页一个 `h1`；键盘每个键有读音名称。

**截图**
- [ ] 390 / 1280 × 浅色 / 深色的截图矩阵都看过，并与上一版本对比。
- [ ] 截图一律是视口截图（整页截图会把固定定位的键盘画到页面中间）。

**文档**
- [ ] README、`help.html`、What's new 与改动一致（`AGENTS.md` 的文档同步规则）。
- [ ] DESIGN.md 已更新，或在任务文档中写明不需要更新的理由。

## 6. 记录

`release-review.md` 至少包括：候选提交哈希、截图目录、三份报告的位置、综合问题表（来源、是否核实、级别、处理方式）、审核清单结果、真机确认结果、最终结论（可以发布 / 阻塞）。
